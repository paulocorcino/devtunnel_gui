# CONTEXT — DevTunnel GUI

Desktop app (Windows, tray) for managing Microsoft Dev Tunnels with an experience
close to paid solutions (ngrok/expose style), pragmatically and without over-engineering.

## Glossary

### Tunnel
A logical resource in the Microsoft Dev Tunnels service, identified by a **Tunnel ID**.
Can contain one or more **Ports**. Has expiration and access rules.

### Requested Tunnel ID vs Real Tunnel ID
When creating a tunnel with a desired name (e.g. `paulo-desktop-3000`), the service
returns a **Real Tunnel ID** with a generated suffix + region (e.g.
`paulo-desktop-diad0dn-3000.brs`). The requested name ≠ the real ID. The app must
store the mapping.

### Group
An organizational concept in the app that maps **1:1 to a Dev Tunnel**. The user
creates named groups (e.g. `frontend`, `apis`) and allocates ports to them.
One group = one Tunnel ID = one host connection. Deleting a group deletes the tunnel
and all its ports; deleting a port does not affect the others.

### Port
A local port exposed inside a tunnel/group, with a **Protocol** (http/https/auto).
**Adding a port always asks for the destination group** (dropdown with a selected
default + inline "new group" option). The fast path is: port number → Enter.

### Host
The act of keeping the tunnel alive, serving local port traffic to the public URL.
In the native model, hosting runs **inside the app process** via the SDK
(Tunnel Host Connections), not as an external process.

### Public URL
The public URL generated by the service to access the hosted port
(e.g. `https://<tunnel>.<region>.devtunnels.ms`).

### Keep-alive (Liveness)
Keeping a group's host connection alive, reconnecting if the relay drops.
Responsibility of the SDK running in-process. Distinct from the health probe.

### Health probe (Operational)
A periodic HTTP probe against the Public URLs of **hosted** groups, classifying
them into **3 states**:
- **Operational:** relay routed to the upstream and it answered (any 2xx/3xx, and
  also app-level 4xx like 401/404 — the service is reachable).
- **Tunnel ok, service down:** relay reached but upstream unreachable — confirmed
  empirically (Stage 5) as a relay-emitted **HTTP 502/503/504**. Reproduced by hosting
  a port configured `https` while the local server speaks plain HTTP: the local service
  is up but the relay returns 502. Classification is by status code alone (the gateway
  codes are emitted by the relay, not the app), so no body-string matching is needed.
- **Down:** URL unreachable (network/timeout/DNS error) — relay down or group not hosted.

Method: GET `/`, timeout ~5s, interval **configurable, conservative default 60s**,
only for active groups. Works because tunnels use **anonymous access** (an
authenticated URL would redirect the probe to the login page).

## Resolved decisions

- **Architecture (native sweet spot):** native is concentrated where it delivers real
  value (hosting). (see ADR-0001)
  - **Account management** (create/list/delete/port/access/update) → one-shot subprocess
    calls to `devtunnel.exe` directly (NOT PowerShell), via `std::process::Command`.
    Fast operations, no long-running process pain. Required because the *user*
    (account-level) token only exists in the system secure keychain, with no documented
    command to extract it.
  - **Hosting** (keep-alive, long-running) → Rust `tunnels` SDK in-process
    (Tunnel Host Connections), authorized by a host-scoped token minted with
    `devtunnel token <id> --scopes host`.
- **Language:** Rust — the only option with both Management API **and**
  Tunnel Host Connections in the official SDK (Go lacks hosting). `tunnels` crate from
  the `microsoft/dev-tunnels` repo, actively maintained (2026), v0.1.0, feature `connections`.
- **PowerShell:** eliminated. The CLI is called as a direct binary, not via PS scripts.

### Hosting — validated (spike #2, see docs/spikes/0001-sdk-hosting.md)
SDK hosts in-process ✓ (curl to the Public URL reached the local server, no external
`devtunnel host`). Learnings:
- Needs **two** tunnel tokens: `host` (in `connect`) and `manage:ports`
  (default auth of the mgmt client, otherwise `add_port` returns 401). Mint one per
  call (repeating `--scopes` corrupts the first to "shost").
- Token expires in **~24h** → long-running keep-alive requires re-minting + reconnect.
- Build requires NASM + Strawberry Perl + `vendored-openssl` on Windows (dev cost;
  end users receive a prebuilt binary). The `spike` feature isolates all of this from the GUI.

## Model decisions

- **Tunnel model:** manual grouping. Group = Tunnel (N ports). One host connection
  per group. Adding a port always picks the destination group.

## UI/runtime decisions

- **GUI:** Slint (declarative, Rust, single binary). Tray via `tray-icon` crate
  (integrates into Slint's winit event loop).
- **Runtime:** `tunnels` SDK is async/tokio → runs on a background thread (host
  connections + health probes); communicates with the Slint UI via channels.
  Account management (subprocess `devtunnel.exe`) also off the UI thread.

## Lifecycle decisions

- **Auto-start:** starts with Windows (registry HKCU Run), minimized to tray.
- **Auto-resume:** re-hosts groups that were active before the last shutdown.
- **Close (X):** goes to tray; fully quitting only via the tray menu.
- **Login expiry (Microsoft-imposed limit):** the CLI login token is valid for only a
  few days. When auto-hosting fails due to expired login, the app enters a **"Re-login"**
  state: warning icon in the tray + Windows notification + "Sign in" button that triggers
  `devtunnel user login` (opens browser). There is no truly eternal keep-alive without
  periodic re-authentication.

## State decisions

- **Source of truth:** the Dev Tunnels service. On startup and periodically,
  `devtunnel list -j` + `devtunnel port list -j` rebuild the view. Local JSON
  (`%APPDATA%\devtunnel-gui\`) stores only: the set of groups to auto-host +
  settings (probe interval, auto-start). Light cache to paint the UI instantly
  before reconciliation.
- **Robust parsing (confirmed):** the CLI supports `-j/--json` on list/show/port,
  so the subprocess returns structured JSON — no more regex-scraping the Real Tunnel ID
  that caused pain in the current script. Commands also accept `--access-token`.

## MVP scope (v1)

**Core:** create/list/delete groups · add/remove ports (always choosing a group) ·
host/stop group · auto-start + auto-resume · 3-state probe @60s ·
tray with window toggle · re-login flow.

**Extras included:** copy URL + open in browser (app and tray) · expiration
auto-renewal (renews tunnel **AND** reapplies anonymous access ACE — both expire) ·
settings panel (probe interval, auto-start, default expiration).

**Notifications:** only the critical **re-login** case (toast + tray alert).
No toasts for normal status changes.

**Out of v1:** QR code, traffic inspection (Inspect URL), multi-account,
labels, tenant/org access control.

### Dialog options (minimal + collapsible "Advanced")
- **Group:** name, expiration (default 30d), anonymous (default on), description.
- **Port:** number, protocol (default `auto`), description.
- **Advanced (collapsed):** `host-header`/`origin-header` (value `unchanged` —
  fixes breakage in dev servers like Vite/HMR, webpack, virtual hosts/CORS caused by
  Dev Tunnels rewriting Host→localhost), `request-timeout`
  (0=disabled, useful for SSE/long-polling/large uploads).

## Implementation notes
- **"Stop hosting":** drops the SDK host connection but keeps the group/ports defined
  in the service (they persist, just not served).
- **Group name = Tunnel ID:** sanitize to the accepted format (lowercase,
  alphanumeric + hyphen). Store the name→Real Tunnel ID mapping (with suffix/region).
- **Auto-renewal:** update tunnel expiration and recreate the anonymous ACE, as the
  current script already does.
